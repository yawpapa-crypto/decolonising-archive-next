# Recommendation engine: pre-implementation audit

Completed 4 October 2026 before schema, ranking or UI changes.

## Stack and data
Next.js 16.2.6 / React 19; App Router, Vercel configuration and Supabase SSR cookies. Supabase PostgreSQL 17.6 is available. Supabase query client, rather than a recommendation ORM, serves current preferences/saves/collections. Payload's PostgreSQL adapter is installed for other content workflows. Actual hosting invoices and quotas are unavailable: no invented current bill.

Read-only linked database counts: 70 profiles; 50 bookmarks; 259 reading lists; 488 list items; zero explicit follows; 51,057 user_activity_events (41 distinct users), 257 search events. Most activity is heartbeat/pause/resume/start/route telemetry; only 1,170 record_viewed and 6 citation_inserted events. Private note_updated events are not appropriate recommendation inputs. Existing admin-only analytics must not become publicly readable.

Local catalogue: 138 records, 138 public metadata rows, 53 require community authority; 127 regions are Ghana, 10 Côte d’Ivoire variants and one Togo/Ghana. All have period, visual-system, type, source and tags; there are no explicit linked-record IDs. Twelve record types, six periods, seven visual systems, 47 source labels. Rights distinguish metadata-only/linked records from CC0/open images. Metadata is usable for transparent scoring but insufficient for promised global diversity or semantic inference. Foundation JSON and cached provider results exist separately; provider metadata is less structured.

## Existing paths and gaps
- Onboarding/preferences → profiles.interests (six real taxonomy dimensions), research_interests and account metadata fallback → For You reads those choices. Signed-in onboarding/preferences browser journeys remain pending at the user's prior request.
- Save → bookmarks; collection save → reading_list_items → private Library. Current saved-title token weights 3/4, with no central configuration. Unsave removes owned state. No need to recreate these state tables.
- Follow → curatorial_follows → public curatorial_activity chronological feed. Previously implemented RLS/aggregation tests pass. No recommender should reorder it.
- Search/Explore → existing query/provider streams → shared Detail/record/source; explicit Explore currently reads no interest signals. Preserve that separation.
- Related → title-token provider queries with hash ordering; explanations can imply similarity without measuring it. Catalogue links are empty, so no invented graph.
- For You currently generates provider buckets, tags entire query responses with an interest reason, then hashes order. Broad randomly chosen taxonomy labels are called serendipity without demonstrating a bridge; there is no diversity penalty, negative feedback or decomposition inspector.
- Provider fetches use 3.5-second timeout and hourly Next caches; image resolver/proxy already separate. Current first render can await multiple providers/image-pool work. Browser navigation to the running For You page timed out during audit; investigate with the new bounded candidate path rather than claim it loaded quickly.
- Existing analytics stores paths, referrers and technical telemetry, has admin-only reads and privacy opt-out. Reuse a strictly scoped minimal recommendation namespace with owner-only RPCs instead of copying private analytics into a new store.
- Public-record cultural and rights filtering must precede candidate features and run again before rendering. Safe public-profile and public-collection projections already exist.

## Options and decision
| Option | Fit now | Costs and burden | Cold start / explanation / privacy |
|---|---|---|---|
| A: native PostgreSQL state + application metadata ranker | Best: existing state and small catalogue | No new service; bounded existing DB reads and CPU | Explicit choices work immediately; decomposed scores; owner-only signals |
| B: Gorse | Weak collaborative evidence at current volume | Persistent service, cache/storage, backups and monitoring; cannot responsibly quote a bill without a chosen host | Requires clean meaningful feedback; final ARED access/diversity layer still needed |
| C: Gorse candidates + native reranker | Useful later when interaction coverage grows | Same service burden as B plus synchronisation | Good modular long-term direction, currently premature |

Choose A for phase 1. At 138 local records, app-side metadata ranking is simpler than importing a parallel record warehouse into SQL; PostgreSQL holds authoritative user state and events. This is native deterministic personalisation, not a trained model. Gorse explicitly has separate deployment and feedback configuration ([deployment](https://gorse.io/docs/deploy/docker), [configuration](https://gorse.io/docs/config)); do not install it or enable any optional LLM ranking path.

pgvector is available but NOT installed. Defer embeddings: no real linked graph, narrow catalogue, no quality baseline. [pgvector](https://github.com/pgvector/pgvector) supports exact and approximate vector search, but vectors will not fix missing cross-region metadata. Later evaluate ingestion-only multilingual open models with licensing/cultural access review and measured retrieval gains; no browsing-time inference.

## Phase 1 plan
Central weights and pure ranker; real metadata dimensions; separate long-term/current-session contributions; saved/collection/follow state and scoped events; cold-start editorial provenance; defensible shared-metadata bridges; configurable mix/diversity/negative feedback; deterministic explanations; bounded cached providers outside scoring; existing image resolution after ranking; quiet More/Less controls and development-only inspector. No new paid service, ML dependency, public telemetry, fake users or Following ordering change.

## Implementation and final report — 4 October 2026

1. **Previous architecture:** provider-query buckets and title-token/hash ordering; unmeasured explanations and no negative-feedback/diversity decomposition. The audit above was completed first.
2. **Stack:** Next 16.2.6, React 19, Supabase SSR/PostgreSQL 17.6; native Supabase client. Existing Vercel and Supabase infrastructure retained.
3. **Available interactions:** 70 profiles, 50 bookmarks, 259 lists, 488 items, zero follows at audit time. Most of 51,057 analytics rows are lifecycle telemetry, not useful collaborative feedback. No private-note content imported.
4. **Metadata:** 138 local records; 53 require authority and are excluded. Strong Ghana coverage, weak cross-region coverage, no explicit linked-record graph. Only actual dimensions/values are used. External provider metadata is literal and less complete; unknown country is not invented.
5. **Gorse suitability:** deferred. Meaningful shared interactions are too sparse to establish collaborative gains. A future independent candidate service must remain behind ARED's access and diversity reranker.
6. **Native suitability:** selected. PostgreSQL provides authoritative owned preferences/state and minimal events; a pure application ranker handles the small catalogue. This is deterministic personalisation, not model training.
7. **pgvector:** available, not installed. Revisit only after a broader metadata baseline and an ingestion-only, licensed open embedding evaluation demonstrate gains.
8. **Selected architecture:** owned PostgreSQL state → explicit/behaviour/session features → native and public-provider candidates → decomposed scoring → diversity/bridge selection → current access check → existing image/cover hydration. No browsing-time generative inference.
9. **Services/packages:** none added for recommendations. No Gorse, embedding runtime, paid recommendation API or new dependency.
10. **Schema changes:** migrations `20261004030000` and `20261004040000`, applied to the linked project. Reuse `user_activity_events` with a recommendation namespace, partial owner/time index, bounded owner-only RPCs and authoritative state-change triggers. No new tables; existing public projections retained.
11. **Collected signals:** record/source/related opens, More/Less, vocabulary-only search themes and delivery counts; DB triggers record save/unsave, collection add/remove, follow/unfollow from either app or web. Saves, collections, follows and explicit preferences are read from current authoritative state rather than repeatedly counting historical additions. Collection/profile opens and impressions have configured weights but are not currently instrumented. Raw recent query strings remain in tab-local session storage for at most two hours; server event terms are limited to recognised public vocabulary.
12. **Weights:** collection 10; save/follow/More 8; source 5; related/repeated theme 4; collection open 3; record open 2; profile open 1; impression 0. Explicit choices start at 12. Caps and time decay prevent large histories dominating. Configuration is in `lib/recommendations/engine.ts`.
13. **Candidate generation:** all currently eligible local metadata plus bounded hourly-cached Commons/Open Library/OpenAlex streams. Public query pools are shared; personal profiles are not cached globally. External candidates must demonstrate literal metadata overlap with their generation query. No invented or private collections/users.
14. **Ranking:** separate preference, saved similarity, collection, followed public material, current session, historical behaviour, editorial, verified visual availability, novelty, saved repetition and negative components. Shuffle only changes tied ordering; it does not manufacture a bridge. Native related records require measured shared metadata. Restricted native seeds cannot fall through to external related queries.
15. **Diversity:** greedy soft penalties for repeated region, type, source, creator, period and visual system; configurable two-consecutive threshold. This cannot create missing countries. The canvas presents ranked data in a spatial masonry layout, so adjacent screen tiles need not correspond exactly to sequential ranked positions.
16. **Serendipity:** outside dominant geography with an actual shared non-geographic feature. Close/adjacent/bridge targets are 60/25/15, subject to available evidence. No random unrelated filler. The tested guest batch reports zero bridges, rather than falsely claiming 15%.
17. **Cold start:** public editorial starting points, source/type diversity and optional explicit interests. Guests can browse and give temporary feedback. Explanations do not pretend a guest has a behavioural profile.
18. **Explanations:** deterministic reasons from the strongest actual metadata match. Quiet “Why this?”, More/Less and status messages; keyboard focus, Escape and bounded mobile popup. Numeric scores remain in the development inspector.
19. **Following:** no feed-ranking change. Explicit relationship, grouped public activity and chronology remain separate. Existing SQL isolation/unpublication tests were rerun successfully.
20. **Suggested profiles:** actual public curators of overlapping public collections, excluding self/already followed profiles, with real saved/feature overlap. No follower-count ranking. Hidden when evidence is absent; guest API honestly returns an empty module. Real signed-in suggestion UI remains pending.
21. **Suggested collections:** public collections sharing saved records or actual interests, excluding own/already followed and collections without novel material. Bounded safe public record projection, no private collection notes. Available quietly within explanation context for members.
22. **Privacy/access:** cookie-authenticated owner RPCs; no anonymous event/history access, no admin telemetry exposed, same-origin write checks, bounded/validated payloads, current cultural/public metadata filtering and post-ranking check. Followed-person evidence uses the safe public actor projection. Event reads cover 90 days/500 rows; writes prune to 90 days/1,000 owner rows. Opt-out disables optional browsing-event collection/profile use; authoritative save/collection/follow changes still remain normal account state and action counts. Clearing discovery history also clears this tab's current intent and cached For You feedback. No note bodies, IP, referrer, mouse movement or raw paths copied into recommendation events.
23. **Fallback:** absent auth/preferences/provider failures still yield eligible native editorial records. Image failure uses the existing typographic tile. Missing/private/restricted related seeds fail closed. Empty suggestions stay hidden. Exhausted finite candidate pools show an honest archive-edge message.
24. **Caching/performance:** bounded parallel state reads and provider timeouts; hourly public candidate caches; rank before remote visual hydration. Static accession/rights-verified visual inventory avoids resolving images during scoring. It must be refreshed when ingestion changes. Local audit request ~7.5s versus a warm new request ~0.1s; development observations, not production guarantees or a mobile network benchmark. Existing feed pagination/prefetch retained. Personal responses use private/no-store.
25. **Infrastructure estimate:** selected architecture adds $0 in separate service subscriptions; existing database, storage, server function and bandwidth usage still count toward the existing plan. Actual invoices/remaining quotas are unknown. Writes are bounded to 1,000 rows per owner and 90 days (70 users would cap at 70,000 rows; actual byte/WAL cost requires production measurement). Future Gorse planning assumption: one shared CPU, 1–2GB RAM, ~10GB volume, existing Postgres, single region, small metadata/ID-only traffic. An illustrative 1GB Fly machine is $6.70–8.50/month in the documented examples, plus $1.50 for a 10GB volume; budget approximately $10–25/month for a small single instance with traffic/backup headroom, excluding a new database, paid monitoring, redundancy and maintenance. This is a planning estimate, not a benchmarked Gorse requirement or purchase. Additional machines/DB can materially raise costs. Rates checked against [Fly pricing](https://docs.fly.io/about/pricing/); no service provisioned.
26. **Files:** new `lib/recommendations/{engine,catalogue,server,client}.ts`, visual inventory JSON, recommendation event/suggestion API routes, development inspector, RecommendationHistory, CuratorialSuggestions and SourceLink; updated For You server/API/feed/tile/detail/CSS, SearchBox, preferences, SettingsModal, native record source link and the 768px navigation breakpoint. Two migrations and three recommendation test files. Existing unrelated working-tree edits preserved. See this audit and `artifacts/recommendations/`.
27. **Verification:** eight pure-engine scenarios pass; HTTP tests cover cold start, access, pagination/deduplication, negative guest feedback, authentication/origin/validation, related metadata, restricted related seed and empty suggestions. Rolled-back linked-DB fixtures verify owner isolation, exclusion of private analytics, deduplication, latest feedback, state-change save/collection/follow metrics and clear-history; no QA users persist. Following SQL privacy tests pass. TypeScript passes and focused recommendation ESLint has zero errors/warnings. Full production build/deployment is not claimed: the earlier production environment has blank Supabase overrides and needs separate configuration repair. Signed-in onboarding, real save/follow/publish, cross-device sync and personalised suggestion journeys remain pending at the user's instruction.
28. **Browser/screenshots:** actual app tested at 1440/1280/1024/768/430/390/375, document widths equal viewport widths. Reviewed For You screenshots, mobile explanation and Following; checked More/Less status, loading, finite-pool state, explicit search and navigation. At 768px navigation crowded search; breakpoint corrected to existing mobile layout. The Palestinian architecture query was preserved verbatim and real architecture/Palestine records returned; For You then displayed a current-intent reason. Screenshots are local artifacts, not screenshot-based ranking data.
29. **Limits:** Ghana-heavy local catalogue; some provider responses have only generic title metadata; no trained collaborative model, semantic vectors, guaranteed geographic mix or measured conversion uplift. Suggestions need actual public curation evidence. Delivery counts deduplicate same-sized batches within a minute and are approximate delivered counts, not impressions; no CTR/conversion denominator is fabricated. Retention is opportunistic on writes (stale rows of inactive accounts need scheduled cleanup if strict physical erasure deadlines are required). Existing canvas fades/dynamic layouts remain; historical screenshot captures can show intermediate transition states. External related fallback now requires a shared literal title term and labels that evidence honestly; it remains weaker than native metadata relations. A session/current query is bounded, not a permanent replacement of chosen interests.
30. **Next phase:** finish pending signed-in QA when available; improve cross-region/authority-reviewed ingestion and canonical provider metadata, refresh visual inventory automatically, and collect enough deliberate interactions to evaluate a held-out baseline. Compare Gorse candidates against the native model for relevance, repetition, source/region coverage and defensible novelty before hosting it. Add ingestion-only vectors or learned ranking only after measured gains and cost/privacy review.
